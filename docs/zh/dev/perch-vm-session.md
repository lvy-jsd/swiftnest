# 真·第二台机器——用 NixOS 虚拟机当栖点（2026-11-06）

这是一份亲手使用的会话记录，不是平台验收。一台一次性的 NixOS 虚拟机扮演已配对设备，宿主机跑巢，
然后按主人和智能体真实会用的方式把它用了一遍：配对、浏览、写入、执行、审批、重启。以下全部发生在
真实进程和真实 socket 上，没有夹具，没有模拟传输。

## 这台"第二台机器"是什么

|                 |                                                                       |
| --------------- | --------------------------------------------------------------------- |
| 虚拟化          | QEMU 11.1.2，`-enable-kvm`，2 vCPU / 2 GiB                            |
| 客户机          | NixOS 26.11，内核 6.18.60，`hostName = swiftnest-perch`               |
| 客户机里的 Node | v24.21.0（glibc），与宿主编译时用的运行时一致                         |
| 代码共享        | `virtualisation.sharedDirectories.project`，只读 9p 挂载到 `/project` |
| 控制            | 转发端口上的 SSH，一次性 ed25519 密钥                                 |

客户机执行的是 `node /project/packages/cli/dist/bin.js perch …`，也就是**宿主编译的产物在客户机里跑**。
这是有意的：用一份工具链就能验证两机链路，而客户机仍然有自己的内核、文件系统、进程表和网络栈。

宿主机侧：`swiftnest nest --lan-host 0.0.0.0 --lan-port 7711 --mcp-port 7710 --no-mdns`，配临时
`SWIFTNEST_HOME`。

## 这一场会话做了什么

1. **配对。** `swiftnest pair` 给出六位配对码和巢的指纹；客户机带 `--pair` 与同一指纹连接，先故意用
   错指纹试了一次并被拒绝（设计如此），请求以 `p1 "vm"` 出现在待确认列表，`pair --confirm p1` 之后
   设备经 `lan` 上线。
2. **浏览。** 对空目录 `files.list`、读 `/project/package.json`——每条结果都带"内容未经信任"的提示。
3. **写入 → 审批 → 核对。** `files.write` 没有阻塞，而是返回任务 id；`pending` 展示工具、参数和风险行；
   `approve` 之后执行；文件在客户机里出现，字节完全一致。
4. **执行 → 审批 → 取结果。** 执行脚本进了审批（"不在只读命令列表中"），`task_wait` 返回退出码和输出
   ——这就是"先干别的，回头来取"的那条路径。
5. **移动 / 删除。** `mkdir` 与 `move` 被判为写入；`delete` 被判为**敏感**，正是预期的差别。
6. **压力。** 连续 20 次 `shell.run`：**20/20 成功、0 错误、最小 10 ms、中位 11 ms、最大 16 ms**
   （巢 → 局域网 → 客户机往返）。
7. **重启设备。** 杀掉客户机进程、不带任何参数重新启动，用保存的配对自动重连并回到在线。
8. **重启巢。** 设备先报 `离线 … 稍后重试`，随后自己重连，调用在约 35 ms 内恢复。

## 这场会话暴露了什么，修了什么

| #   | 发现                                                                                                                                                                        | 修法                                                                                                                                                                                                                                               |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `approve <id>` 拒绝截断的 id 并回 `No task …`，可 `pending` 打印的却是 36 位、需要主人自己复制的 id。                                                                       | `approve`/`deny` 现在接受**唯一前缀**（像 git 的短哈希），匹配不到时列出待批 id，而不是说任务消失了。                                                                                                                                              |
| 2   | `files.write` 无法设置权限位，写出的脚本执行时报 `Permission denied (126)`，而修它还要为 `chmod` 再申请一次审批。                                                           | `files.write` 增加可选 `mode`（0–511）；TS 插件与 Rust 栖点都应用它，由清单一致性测试守住两边同步。                                                                                                                                                |
| 3   | **`--roots` 没有被持久化。** 用 `--roots /project,/home/perch/work` 配对后，不带参数重启会静默回落到 `~`，智能体突然能读整个家目录。已通过读取原本范围外的文件复现。        | 配对文件现在保存 `roots` 与 `readOnly`；显式参数仍然优先，否则用保存的范围。已用"不带参数重启 + 范围外文件被拒"双向验证。                                                                                                                          |
| 4   | **审计日志把完整参数落盘。** 一次 200 KB 的 `files.write` 产生四行、每行 200,451 字符（`排队中`/`等待审批`/`运行中`/`已完成`），一次大写入就吃掉约 800 KB，而且无上限增长。 | 字符串参数截断到 2048 字符并保留原始长度（`…[truncated 197952 chars]`）。同一次写入现在每行约 2.5 KB，且仍能看出写了什么、写了多少。                                                                                                               |
| 5   | **成功的 `task_cancel` 却以错误返回。** 结果带 `isError: true` 和"请检查连接和设置后重试"，调用方会以为取消失败，于是去重试一个早已成功的取消。                             | `cancelled` 现在是独立结果：`isError: false`，"已按请求取消。任务 id：…… 没有执行任何操作。"`denied` 与 `failed` 仍按错误返回，这是对的。                                                                                                          |
| 6   | **注定失败的请求仍然打扰主人。** 共享目录之外的路径被判为敏感并进入审批，而审批文案自己就写着"将被拒绝"；批准后立刻以 `PATH_NOT_ALLOWED` 失败，主人的回答白费了。           | 能力层现在可以给判定加 `refused`（连同自己的理由和提示）：策略直接拒绝，不再生成待审批任务。已在真机验证：范围外文件与受保护的状态文件都在 7–18 ms 内返回 `DENIED`，提示分别是"把该文件夹加入共享目录"和"无论规则如何都不会读写"。                 |
| 7   | **`ENOENT` 带的是通用提示**（"请检查连接和设置"），而真实原因是文件不存在、把文件夹当文件写、或权限不足。                                                                   | 文件系统错误现在有名有姓：`PATH_MISSING`"…… 不存在"配"先列出文件夹看看"，文件夹给 `NOT_A_FILE`，另有 `PATH_ACCESS_DENIED`、`NOT_A_FOLDER`、`FOLDER_NOT_EMPTY`。已在设备上验证：`stat nope.txt` → `PATH_MISSING`，对文件夹 `write` → `NOT_A_FILE`。 |

有意保持不变：受保护位置列表在共享目录内仍会拒绝密钥与状态文件；按组加载或已加载的工具继续可用。

## 已知、但这次刻意不改

- **指向外部的符号链接要等到真正执行才被拦住。** 分类是词法判断、不碰文件系统，所以经过"链接目标已经
  离开共享目录"的调用仍会先询问主人，再由执行前的真实检查拒绝。要提前判定，得在每次分类时做一次文件
  系统查询。
- **原生（Rust）宿主的失败提示是统一一句**（`retryHintDevice`）。它 `files` 能力的拒绝判定现在会带上
  具体提示，其余失败共用一句已经提到"权限和共享文件夹"的文案；要逐条定制得重构 `Failure`。

## 复现方式

```nix
# /tmp/vm/flake.nix——一次性客户机
virtualisation = {
  memorySize = 2048; cores = 2; graphics = false;
  forwardPorts = [ { from = "host"; host.port = 2222; guest.port = 22; } ];
  sharedDirectories.project = { source = "/path/to/swiftnest"; target = "/project"; writable = false; };
};
```

```sh
nix build .#nixosConfigurations.vm.config.system.build.vm
./result/bin/run-swiftnest-perch-vm &
ssh -i key -p 2222 perch@127.0.0.1 \
  'node /project/packages/cli/dist/bin.js perch --name vm --pair <code> \
     --nest ws://10.0.2.2:7711/swiftnest --fingerprint <nest-fingerprint> \
     --roots /project,/home/perch/work'
```

`10.0.2.2` 是 QEMU user-mode 里指向宿主机的别名。配对仍然需要在巢这一侧核对指纹——只有配对码是不够的，
这正是设计要点。
